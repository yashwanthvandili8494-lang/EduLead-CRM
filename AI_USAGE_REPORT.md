Include validation rules that prevent leads from being marked as CONVERTED without official admission ID and fee payment details, mandate a documented reason when marked LOST, and generate an immutable activity audit timeline for institutional accountability."*

### CODE I MODIFIED: What part?
1. **Dual-Mode Database Adapter (`server/config/db.js`):** Added an intelligent fallback mechanism that detects if a local MongoDB server is available or seamlessly switches to an embedded in-memory database engine (`mongodb-memory-server`) with automatic seeding so evaluators can run the project out-of-the-box with zero configuration.
2. **Duplicate Contact Checker (`server/controllers/leadController.js`):** Enforced a real-time pre-submission check on phone numbers and emails to notify users if a lead already exists from another channel (e.g. initial Website inquiry followed by WhatsApp message) with options to merge or link.
3. **Role-Based Privacy Safeguards (`server/controllers/leadController.js` & `server/middleware/auth.js`):** Restricted counsellors strictly to viewing and modifying their assigned leads, while allowing Admins and Managers institutional-wide visibility, bulk reassignment privileges, and analytics access.
4. **1-Click Reviewer Role Switcher (`client/src/components/Navbar.jsx`):** Added a topbar role switch bar allowing walk-in interviewers to instantly switch between Admin, Manager, and Counsellor accounts without manual logout/login cycles.

### AI OUTPUT THAT WAS WRONG:
- In an early generated status transition handler, the code allowed changing any lead's status to `CONVERTED` without validating whether tuition fee or admission ID were supplied.
- Additionally, the initial duplicate check simply threw a unique key conflict error (`code: 11000`) crashing the creation flow rather than presenting a helpful user-facing warning and allowing secondary linkage.

---

### HOW I IDENTIFIED THE PROBLEM:
- Tested the API against negative test cases (e.g., attempting to mark a lead converted with empty fields, and submitting the same student phone number from both "Website" and "WhatsApp" forms). The missing validation allowed invalid state changes, and the raw duplicate error gave a cryptic database rejection instead of an actionable CRM prompt.

---

### HOW I FIXED IT:
- Implemented strict server-side validation middleware:
  - Transition to `CONVERTED` strictly requires `admissionId`, `feePaid`, `receiptNumber`, and `enrolledAt`.
  - Transition to `LOST` strictly requires a categorical `lostReason`.
  - Created a dedicated `checkDuplicate` endpoint (`POST /api/leads/check-duplicate`) in real-time debounced input, and added a user-friendly duplicate conflict modal that lets counsellors view matching historical records or confirm creation as a linked secondary inquiry.
